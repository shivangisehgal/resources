# High-Level Design Notes

## 1. Networking Basics and Network Protocols

When two computers need to communicate with each other over a network, they follow a defined set of rules called **network protocols**. A network protocol specifies how communication is initiated, how data is formatted and transmitted, and how the receiver interprets that data.

The notes loosely relate networking to the OSI layers:

1. Application layer
2. Presentation layer
3. Session layer
4. Transport layer
5. Network layer
6. Data Link layer
7. Physical layer

At the application level, communication can happen using different models. A client may communicate with a server using HTTP, TCP/IP, FTP, SMTP, sockets, and similar mechanisms. Communication may also occur using a peer-to-peer model, where nodes communicate directly with each other instead of relying completely on a central server.

A useful distinction is that a **connection-oriented protocol** establishes and maintains a connection between two systems, whereas a **connectionless protocol** sends packets without maintaining such a connection. HLD_Merged

---

# 2. Why Network Protocols Are Needed

Network protocols provide a standard way for different devices to exchange information.

They are important because they provide:

- **Interoperability:** Devices built using different technologies can still communicate with one another.
- **Reliability:** Protocols can ensure that data reaches its intended destination.
- **Efficiency:** Protocols help optimize data transmission, latency, and packet usage.
- **Scalability:** Standard communication mechanisms allow systems to grow without redesigning communication from scratch.
- **Security:** Protocols such as SSL/TLS encrypt data during transmission.

Common examples include TCP/IP and HTTP.

---

# 3. TCP — Transmission Control Protocol

TCP is a **connection-oriented transport-layer protocol**.

Before actual application data is transferred, TCP establishes a connection between the sender and receiver.

The connection establishment process involves the familiar handshake:

```text
Client                     Server

SYN ---------------------->

     <---------------- SYN + ACK

ACK ---------------------->
```

After the connection has been established, data transmission can begin.

TCP provides reliability by making sure that packets are successfully received. If packets are lost, TCP can retransmit them. TCP also helps ensure that data is delivered in the correct order.

Because of these guarantees, TCP is useful in applications where **data integrity is more important than minimizing latency**.

Typical examples include web communication and email delivery.

The Internet Protocol, or IP, is responsible for addressing and routing packets to the appropriate destination. TCP operates above IP and provides reliable transport between those endpoints. HLD_Merged

---

# 4. IP — Internet Protocol

IP assigns an address to devices and helps route packets across a network.

Every device communicating through IP has an IP address that identifies its network location.

The basic responsibility of IP is therefore to determine **where a packet needs to go**, while protocols such as TCP determine **how reliably that packet should reach the destination**.

---

# 5. UDP — User Datagram Protocol

UDP is a lightweight, **connectionless** transport protocol.

Unlike TCP, UDP does not establish a reliable connection before sending data. It also does not guarantee:

- packet delivery,
- packet ordering,
- retransmission of lost packets.

Because UDP provides fewer guarantees, it introduces less overhead and can provide lower latency.

UDP is therefore commonly used in latency-sensitive applications such as:

- online gaming,
- VoIP,
- live audio/video communication,
- other real-time systems.

The trade-off is straightforward: **TCP favors reliability, whereas UDP favors speed.** HLD_Merged

---

# 6. HTTP and HTTPS

HTTP stands for **Hypertext Transfer Protocol**.

It is an application-layer protocol primarily used for communication between web clients and web servers.

For example, a browser sends an HTTP request to a server, and the server returns an HTTP response containing the requested resource or data.

HTTPS is HTTP with an additional security layer.

HTTPS uses encryption so that information exchanged between the client and server cannot easily be read or manipulated by an intermediary.

Therefore:

```text
HTTP
Client <------------> Server

HTTPS
Client <---- Encrypted Connection ----> Server
```

HTTPS provides confidentiality and improves communication security during transmission. HLD_Merged

FTP is used for transferring files between a client and a remote server.

**SMTP — Simple Mail Transfer Protocol**

SMTP is used primarily for sending emails.

Other protocols such as POP and IMAP may be used for retrieving emails.

The important interview point is that different application-layer protocols were designed for different communication requirements.

# 8. Proxy Servers

A **proxy server** acts as an intermediary between a client and another server.

Instead of communicating directly with the destination server, the client communicates with the proxy. The proxy then communicates with the destination server on behalf of the client.

```text
Client → Proxy Server → Actual Server
```

Proxy servers may be used for several purposes:

- content filtering,
- privacy or anonymity,
- security and access control,
- caching,
- load balancing.

Different forms of proxies mentioned in the notes include:

- forward proxy,
- reverse proxy,
- web proxy,
- public proxy.

A proxy can improve security and performance, but it introduces additional infrastructure and configuration complexity. HLD_Merged

# 9. CAP Theorem

CAP stands for:

- **C — Consistency**
- **A — Availability**
- **P — Partition Tolerance**

The CAP theorem applies to distributed systems.

### Consistency

Consistency means that clients should observe the same latest value regardless of which replica they query.

For example, suppose a value is updated from:

```text
B = 2
```

to:

```text
B = 5
```

Once the update succeeds, every relevant replica should eventually expose the appropriate updated state according to the consistency guarantees of the system.

### Availability

Availability means that every valid request should receive a response from the system, even if the returned data is temporarily stale.

### Partition tolerance

Partition tolerance means that the distributed system continues to operate even when network communication between different nodes is interrupted.

In a distributed system, network partitions must be considered. During a partition, the main trade-off generally becomes:

```text
Consistency vs Availability
```

The notes therefore emphasize that a distributed system cannot simply guarantee all three properties perfectly during a partition. HLD_Merged

---

# 10. ACID

Traditional relational databases frequently provide **ACID transactions**.

ACID stands for:

### Atomicity

A transaction should either complete fully or not happen at all.

For example, if a bank transfer involves:

```text
Debit Account A
Credit Account B
```

both operations should succeed together. If one operation fails, the complete transaction should be rolled back.

### Consistency

A transaction should move the database from one valid state to another valid state while preserving database constraints.

### Isolation

Concurrent transactions should behave as though they are operating independently without corrupting one another's intermediate state.

### Durability

Once a transaction has successfully committed, its data should remain stored even after failures.

---

# 11. BASE

Some distributed databases follow weaker consistency guarantees represented through **BASE**:

- **Basically Available**
- **Soft State**
- **Eventually Consistent**

Instead of requiring every replica to contain exactly the same value immediately, an eventually consistent system allows temporary inconsistencies.

Given sufficient time and no further updates, replicas eventually converge toward the same state. HLD_Merged

### MongoDB

# 13. Monolithic Architecture

In a monolithic architecture, most application functionality is packaged and deployed together as one application.

For example:

```text
Application
├── User Management
├── Orders
├── Payments
├── Billing
└── Authentication
```

All of these modules may exist inside one deployable application.

Advantages include initial simplicity and easier development for small applications.

However, as the application grows, problems may include:

- a large and tightly coupled codebase,
- difficulty scaling only one specific feature,
- more complicated deployments,
- slower development and CI/CD,
- one change potentially affecting unrelated functionality.

---

# 14. Microservices Architecture

A microservices architecture decomposes an application into smaller, independently responsible services.

For example:

```text
Order Service
Payment Service
Account Service
Authentication Service
Billing Service
```

Each service should ideally focus on a specific business capability.

Potential advantages include:

- independent scaling,
- easier maintenance,
- independent deployment,
- smaller codebases,
- teams being able to own separate services.

However, microservices introduce distributed-system complexity.

If the decomposition is poor, the system can suffer from:

- increased network latency,
- difficult monitoring,
- failures propagating between services,
- distributed transaction problems,
- data consistency challenges.

For example, when one operation involves Order Service, Inventory Service and Payment Service, failure of one service may leave data inconsistent unless the workflow is designed correctly. HLD_Merged

---

# 15. How to Decompose Microservices

The notes describe a few important decomposition approaches.

## Decomposition by Business Capability

Each service corresponds to a high-level business responsibility.

For an e-commerce system, possible services include:

```text
Order Management
Payment Management
Account Management
Login Management
Billing Management
```

The objective is to group functionality according to what the business actually does.

## Decomposition by Subdomain

A larger business domain may be divided further into smaller subdomains.

For example:

```text
Order Domain
├── Order Tracking
├── Order Placement
└── Order Fulfilment
```

Similarly:

```text
Payment Domain
├── Forward Payment
└── Reverse Payment
```

This approach is related to concepts from Domain-Driven Design.

## Service per Team

A service can also be designed so that a team has clear ownership of a particular service or business responsibility. HLD_Merged HLD_Merged

# 16. Database per Service

Once an application has been divided into independent services, the next question is how those services should store data.

One approach is:

```text
Service A → DB A
Service B → DB B
Service C → DB C
```

This is the **database-per-service** pattern.

Its major benefit is loose coupling. One service cannot freely query and modify the internal tables of another service.

The disadvantage is that operations spanning multiple services can no longer rely on one traditional database transaction.

That problem leads to patterns such as **Saga**.

---

# 17. Shared Database

Another possibility is:

```text
Service A
Service B  → Shared Database
Service C
```

This can simplify joins and ACID transactions.

However, a shared database tightly couples services.

One service's schema changes can affect several other services. Scaling the database independently can also become more difficult.

For microservices, the notes therefore lean toward database-per-service and solving distributed transactions separately. HLD_Merged

---

# 18. Strangler Pattern

The **Strangler Pattern** is used when migrating an existing monolithic application gradually toward microservices.

Instead of rewriting the entire application at once, new functionality is implemented around the existing legacy application.

Traffic can gradually be redirected from the old implementation toward the new services.

Initially:

```text
Request
   ↓
Legacy Monolith
```

During migration:

```text
             ┌→ Legacy
Request → Router
             └→ Modern Service
```

Eventually:

```text
Request
   ↓
Modern Services
```

The main ideas are:

- gradual migration,
- coexistence of old and new systems,
- incremental replacement,
- controlled change instead of a big-bang rewrite.

This reduces migration risk. HLD_Merged

---

# 19. Saga Pattern

A Saga is used to manage a transaction that spans multiple microservices.

Suppose creating an order involves:

```text
Order → Inventory → Payment
```

Each service has its own database.

A traditional ACID transaction cannot easily wrap all three independent databases.

Instead, the process is divided into multiple **local transactions**.

If everything succeeds:

```text
Create Order
      ↓
Reserve Inventory
      ↓
Process Payment
```

If one step fails, previously completed operations may need corresponding **compensating transactions**.

For example:

```text
Create Order ✓
Reserve Inventory ✓
Payment ✗

Then:

Release Inventory
Cancel Order
```

The Saga pattern therefore provides a method for handling eventual consistency across services.

---

# 20. Choreography-Based Saga

In choreography, there is no single central coordinator controlling every step.

Each service performs its work and publishes an event.

Another service reacts to that event.

Example:

```text
Order Service
    |
    | OrderCreated
    ↓
Message Broker
    |
    ↓
Customer / Inventory / Payment Service
```

The receiving service processes the event and emits another event.

The important characteristic is:

> Each service knows which event it should react to, but there is no central component explicitly instructing every service what to do.

This makes services more decoupled, although complicated workflows can become difficult to understand.

The notes illustrate this using event channels and message broker communication. HLD_Merged

---

# 21. Orchestration-Based Saga

In orchestration, a dedicated **orchestrator** controls the workflow.

Instead of services deciding independently what happens next, the orchestrator sends commands such as:

```text
Create Order
Reserve Inventory
Process Payment
```

Services return success or failure responses to the orchestrator, and the orchestrator decides the next action.

Therefore:

```text
               → Order Service
Orchestrator   → Inventory Service
               → Payment Service
```

The major distinction is:

**Choreography:** Services react to events.

**Orchestration:** A central orchestrator explicitly controls the sequence.

# 22. CQRS

CQRS stands for **Command Query Responsibility Segregation**.

The fundamental idea is to separate operations that modify data from operations that read data.

Commands include:

```text
CREATE
UPDATE
DELETE
```

Queries include:

```text
READ
SELECT
```

The write side and read side can use separate representations or even separate databases.

For example:

```text
           ┌→ Write DB
Commands ──┤
           │
           └→ Events → Read Model

Queries ─────────────→ Read DB
```

This makes it possible to optimize the write model for transactions while independently optimizing the read model for fast queries.

The trade-off is additional complexity and possible eventual consistency between the two models. HLD_Merged

# 26. Database Replication

Eventually, one database server can become the bottleneck.

Replication can be introduced using a primary/replica architecture.

```text
               WRITE
                 ↓
              Primary
                 |
           Replication
                 ↓
              Replica
                 ↑
               READ
```

Writes are usually directed toward the primary, while read traffic can be distributed across replicas.

This improves read scalability and can provide redundancy.

The notes refer to this as a master-slave architecture.

# 27. Caching

A cache stores frequently requested information in a faster storage layer so that every request does not have to query the database.

Example:

```text
Request
   ↓
Check Cache
   |
   ├── HIT → Return value
   |
   └── MISS → Query DB
                 ↓
             Store in Cache
                 ↓
              Return value
```

Redis is a common caching technology.

Cached entries may have a **TTL — Time To Live**.

Once the TTL expires, the cached value is removed or refreshed.

Caching reduces database load and improves response latency. HLD_Merged

Instead of every user downloading static assets from the application's origin server:


```text
User → CDN Edge → Origin
```

Typical content includes:

- images,
- JavaScript files,
- CSS,
- videos,
- static files.

The main goals are:

- lower latency,
- lower origin-server load,
- better performance for geographically distributed users.

The notes additionally emphasize that users no longer need direct access to the origin for every static resource. HLD_Merged

# 30. Message Queues

Message queues allow different components of a system to communicate asynchronously.

Instead of:

```text
Producer → Consumer
```

the architecture becomes:

```text
Producer → Message Queue → Consumer
```

The producer does not necessarily wait for the consumer to finish processing the work.

This helps decouple the components.

Benefits include:

- asynchronous processing,
- buffering during traffic spikes,
- better fault isolation,
- independent scaling of producers and consumers.

The notes describe the basic producer/subscriber structure. HLD_Merged

# 31. Exchanges, Routing Keys and Messaging

The notes also illustrate broker-based routing.

A producer publishes a message to an exchange, and the exchange decides which queue or queues should receive it.

### Direct exchange

A direct exchange routes messages based on a matching routing key.

```text
Routing Key = A
     ↓
Queue bound to A
```

### Fanout exchange

A fanout exchange broadcasts the message to every queue bound to the exchange.

```text
             ┌→ Queue 1
Exchange ────┼→ Queue 2
             └→ Queue 3
```

### Topic exchange

A topic exchange routes messages based on patterns in routing keys, allowing more flexible many-to-many communication.

# 34. Horizontal and Vertical Sharding

The notes distinguish two ways of dividing data.

### Horizontal partitioning

Rows are divided across databases or tables.

For example:

```text
Shard 1 → Users A–M
Shard 2 → Users N–Z
```

### Vertical partitioning

Columns or logical parts of a table are separated.

For example:

```text
User Identity Table
User Profile Table
User Preferences Table
```

One disadvantage is that queries involving data from multiple partitions can require additional joins or distributed coordination.

The notes mention normalization as one method of reducing unnecessary dependencies and duplicated data. HLD_Merged

# 35. Hashing for Partitioning

A hash function converts an input key into a fixed-size value.

For example:

```text
hash(userId) % N
```

where `N` is the number of servers.

Suppose there are three servers:

```text
hash(key) % 3
```

The result determines which server stores that key.

This approach can distribute data relatively evenly.

However, it creates a major problem when the number of servers changes.

---

# 36. Rebalancing Problem

Suppose initially:

```text
N = 3
```

and placement is calculated as:

```text
hash(key) % 3
```

Later the system scales to:

```text
N = 4
```

Now placement becomes:

```text
hash(key) % 4
```

The result changes for a large percentage of keys.

Consequently, huge amounts of data may need to move between servers.

This is called the **rebalancing problem**. HLD_Merged

---

# 37. Consistent Hashing

Consistent hashing reduces the amount of data that must move when servers are added or removed.

Imagine the hash space as a circular ring.

```text
           S1
       /        \
     K1          K2
    /              \
  S3                S2
    \              /
     K4----------K3
```

Servers and keys are mapped onto this ring.

A key is assigned to the next server encountered while moving around the ring in a defined direction.

When one server is added or removed, only a limited range of keys needs to move.

This is significantly better than recalculating:

```text
hash(key) % totalServers
```

for the entire dataset.

---

# 38. Virtual Nodes in Consistent Hashing

A physical server can be represented by multiple **virtual nodes** on the consistent-hashing ring.

For example:

```text
Physical Server S1
→ Virtual S1-A
→ Virtual S1-B
→ Virtual S1-C
```

Virtual nodes improve load distribution because one physical server participates at multiple points in the ring.

They also reduce uneven partitioning caused by servers being placed poorly on the hash ring. HLD_Merged

# 41. Base62 Encoding

A short URL can use characters from:

```text
a-z
A-Z
0-9
```

which provides:

```text
26 + 26 + 10 = 62 characters
```

This is commonly called **Base62**.

If the short code has length `n`, the total number of combinations is:

```text
62^n
```

A relatively small number of characters can therefore represent a very large identifier space. HLD_Merged

---

# 42. Hash-Based URL Generation

Another way of generating short identifiers is to hash the original URL.

For example, algorithms such as MD5 or SHA could generate a fixed-length digest.

MD5 produces a 128-bit hash.

However, representing the complete hash directly produces a string much longer than desirable for a URL shortener.

Therefore, the hash would need to be truncated or encoded.

Truncation introduces a possibility of collisions, so collision handling becomes necessary.

---

# 43. Central ID Generator Problem

Another option is generating a unique numeric ID and converting the ID to Base62.

For example:

```text
ID = 1258172
      ↓
Base62
      ↓
f9Aa
```

However, if only one centralized ID generator exists, it can become a **single point of failure** and a scalability bottleneck.

A distributed unique-ID generation mechanism is therefore preferable.

# 44. ZooKeeper

The notes mention ZooKeeper as a possible coordination service.

ZooKeeper helps multiple distributed components coordinate with one another reliably.

For a URL shortener, it could be used to assign non-overlapping ranges of IDs to different ID-generator instances.

For example:

```text

Generator 2 → 1,000,001–2,000,000
Generator 3 → 2,000,001–3,000,000
```

Each generator can then issue IDs independently within its assigned range.

This avoids every ID-generation request requiring communication with one global central service. HLD_Merged

# 55. Coordinator Node

A request may first arrive at a coordinator.

For a PUT request:

```text
PUT(key, value)
      ↓
Coordinator
      ↓
Determine responsible replicas
      ↓
Write to replicas
```

The coordinator determines which nodes should contain the key according to consistent hashing and the replication strategy.

The notes mention maintaining a **preference list** of candidate replicas.

---

# 56. Quorum

Instead of requiring every replica to acknowledge an operation, distributed systems commonly use a quorum.

The notes use the standard notation:

```text
N = Number of replicas
W = Required write acknowledgements
R = Required read responses
```

For example:

```text
N = 3
W = 2
R = 2
```

A write can succeed after two replicas acknowledge it.

A read can collect data from two replicas.

Quorum values represent a trade-off among latency, availability, and consistency. HLD_Merged

---

# 57. Hinted Handoff

The notes briefly refer to handling a temporarily unavailable replica.

If a target replica is down, another healthy node can temporarily hold the write on its behalf.

When the failed server recovers, the stored data can be transferred to it.

This prevents temporary machine failure from necessarily causing the complete write to fail.

---

# 58. Data Versioning

Because multiple replicas can accept updates, conflicting versions of the same key may exist.

For example:

```text
Replica 1: cart = version A
Replica 2: cart = version B
```

The system therefore needs a method for determining causality or detecting conflicting updates.

The notes introduce **vector clocks** for this purpose. HLD_Merged

---

# 59. Vector Clocks

A vector clock stores version counters associated with nodes.

Conceptually, a version may look like:

```text
[S1: 2, S2: 4, S3: 1]
```

When a node updates the object, it increments its counter.

By comparing vector clocks, the system can determine whether:

- one version clearly happened after another,
- or two versions evolved independently and are therefore conflicting siblings.

If two versions conflict, the application may need to merge them.

The notes use a shopping-cart example to illustrate multiple updates propagating between replicas. HLD_Merged

---

# 60. Eventual Consistency in Dynamo-Style Systems

A Dynamo-style database emphasizes availability.

Different replicas may temporarily hold different versions of the data.

Over time, replication and reconciliation cause the replicas to converge.

This is an example of eventual consistency rather than requiring strict immediate consistency for every operation.

---

# 61. SQL vs NoSQL

The notes compare relational SQL databases with non-relational NoSQL databases.

## SQL Databases

SQL databases typically store data using structured tables:

```text
Rows × Columns
```

Relationships between entities are explicitly modeled.

They generally use a predefined schema.

Their strengths include:

- structured data,
- complex queries,
- joins,
- relational constraints,
- ACID transactions,
- strong consistency.

SQL databases are often vertically scaled, although distributed SQL systems also exist.

---

# 62. NoSQL Databases

NoSQL means non-relational or "not only SQL."

NoSQL databases are generally selected when applications need flexible data models or large-scale horizontal distribution.

The notes emphasize:

- flexible structure,
- horizontal scalability,
- distributed storage,
- weaker consistency in some systems,
- high availability.

NoSQL does not refer to one specific database model. Several categories exist. HLD_Merged

---

# 63. Types of NoSQL Databases

## Key-Value Database

Information is stored as:

```text
Key → Value
```

Example:

```text
"user:123" → "{...JSON...}"
```

Retrieval is primarily based on the key.

The value is often treated as opaque by the storage engine.

---

## Document Database

A document database also uses key-like identifiers but stores structured documents, often JSON-like.

Unlike a pure key-value store, document databases can query fields within the stored value.

Example:

```json
{
  "name": "Shivangi",
  "age": 24
}
```

A query can potentially search using `name`, `age`, or other document fields.

---

## Column-Oriented Database

Data is organized around column families or column-oriented structures rather than conventional relational rows.

These systems are useful for very large distributed workloads with known access patterns.

---

## Graph Database

Graph databases represent information using:

```text
Nodes
Edges
Relationships
```

For example:

```text
Person A ----friends-with----> Person B
```

Graph databases are useful when relationships themselves are central to the query model. HLD_Merged

---

# 64. SQL vs NoSQL — Interview Summary

The notes contrast them approximately as:

| SQL | NoSQL |
|---|---|
| Relational | Non-relational |
| Defined schema | Flexible schema |
| Complex queries and joins | Usually designed around known access patterns |
| Strong transactional guarantees | Often BASE/eventual consistency |
| ACID | Frequently availability-oriented |
| Commonly vertical scaling | Commonly horizontal scaling |

A database should not be selected merely because SQL or NoSQL is "better." It should be selected according to the application's query patterns, consistency requirements, relationships, scalability requirements, and transaction requirements. HLD_Merged

# 69. Why Peer-to-Peer Chat Alone Is Not Enough

Two users could theoretically communicate directly using each other's IP addresses.

```text
User A ←→ User B
```

However, this is problematic because:

- users may be offline,
- IP addresses may change,
- clients may be behind NAT/firewalls,
- group messaging becomes difficult,
- reliability becomes difficult,
- the design is not sufficiently scalable or manageable.

Therefore, a centralized or distributed chat-server layer is introduced. HLD_Merged

---

# 70. Why Traditional HTTP Is Not Ideal for Receiving Chat Messages

Normal HTTP communication follows a request-response model.

```text
Client → Request
Server → Response
Connection completes
```

This works well when the client initiates communication.

However, chat also requires the server to deliver a message to a client immediately when another user sends one.

If User B sends User A a message, User A may not currently have an HTTP request waiting for the server.

Therefore, plain short-lived HTTP request-response communication is not sufficient for true real-time messaging.

---

# 71. Polling

One solution is polling.

The client repeatedly asks:

```text
"Any new messages?"
```

For example:

```text
Client → Server: New message?
Server → Client: No

5 seconds later...

Client → Server: New message?
Server → Client: No

5 seconds later...

Client → Server: New message?
Server → Client: Yes
```

This is simple but inefficient because most requests may return nothing.

---

# 72. Long Polling

With long polling, the client sends a request and the server keeps the connection open until:

- new information is available,
- or a timeout occurs.

After receiving the response, the client opens another long-poll request.

This reduces unnecessary polling but still requires repeated HTTP connections.

---

# 73. WebSockets

WebSocket provides a persistent **bidirectional** connection between a client and server.

```text
Client ================= Server
        persistent
        bidirectional
        connection
```

After the connection is established:

```text
Client → Server
Client ← Server
```

either side can send information without creating a new request-response connection each time.

Therefore, WebSockets are highly suitable for real-time chat communication.

The notes compare polling, long polling and WebSockets on page 34. HLD_Merged

---

# 74. Multiple Chat Servers

A large chat application cannot run on a single chat server.

Instead:

```text
                    ┌→ Chat Server 1
Users → Gateway/LB ─┼→ Chat Server 2
                    └→ Chat Server 3
```

A connected user maintains a WebSocket with one of those chat servers.

The problem is that the sender and receiver may be connected to different servers.

For example:

```text
User A → Chat Server 1

User B → Chat Server 3
```

Chat Server 1 therefore needs to know that User B is currently connected to Chat Server 3.

---

# 75. User-to-Server Mapping Service

The notes introduce a service that stores the mapping:

```text
UserId → ChatServerId
```

For example:

```text
User A → Server 1
User B → Server 3
User C → Server 2
```

When a user logs in or establishes a WebSocket, their current chat-server assignment is stored.

Suppose User A wants to send a message to User B.

The flow becomes:

```text
User A
   ↓
Chat Server 1
   ↓
Mapping Service
"Where is User B?"
   ↓
User B → Chat Server 3
   ↓
Chat Server 3
   ↓
User B
```

This allows users connected to different chat-server instances to communicate. HLD_Merged

# 79. Handling Chat Server Failure

Suppose User A is connected to:

```text
Chat Server 1
```

and Chat Server 1 crashes.

The user's WebSocket connection breaks.

The client reconnects through the load balancer or service-discovery layer and is assigned another healthy server.

For example:

```text
Before:
User A → Server 1

Server 1 fails

After:
User A → Server 4
```

The mapping service then updates:

```text
User A → Server 4
```

Future messages are routed to the new server.

# 80. Presence / Last Seen

Presence is related to whether a user is currently active.

The notes mention continuously tracking the user's connection state through chat servers.

A presence service can maintain information such as:

```text
ONLINE
OFFLINE
LAST_SEEN_TIMESTAMP
```

When a WebSocket disconnects or the user stops sending heartbeats, the system can update presence information.

The exact consistency requirement can be weaker than payment-type data because being a few seconds stale for "online" status is generally less critical.

# Final Chat Application Architecture from the Notes

Combining the final pages, the architecture broadly becomes:

```text
                         ┌───────────────────┐
                         │ Authentication    │
                         └─────────┬─────────┘
                                   │
                                   ↓
User A ──WebSocket──→ Chat Server / Gateway
                           │
                           ├────────→ User-Server Mapping
                           │             UserId → ServerId
                           │
                           ├────────→ Chat Message Storage
                           │             Cassandra / NoSQL
                           │
                           ├────────→ Presence / Last Seen
                           │
                           └────────→ Other Chat Servers
                                          │
                                          ↓
                                       User B
```

If User A and User B are connected to different chat servers, the user-server mapping allows the source server to locate the destination server.

Messages are persisted in distributed storage so that chat history is not dependent on one chat-server process remaining alive.

The chat servers can therefore remain relatively stateless with respect to permanent message history, while connection state and routing information are handled separately. HLD_Merged
