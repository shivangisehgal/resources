System Design in a Hurry — beginner notes
System design means deciding how the parts of an application work together: where requests go, where data lives, and what happens when traffic grows or a part fails. In an interview, you explain a workable design and the reasons behind your choices. There can be several good answers. Introduction
A basic picture to keep in mind is: user → server → database → server → user. The rest of the guide explains when to add other parts, such as a cache for speed or a queue for slow work.
1. How to prepare
Learn the interview structure, then the basic concepts, technologies, and recurring design patterns. After that, try a design question before reading its worked answer. Practise explaining your design aloud under a time limit; reading solutions alone does not practise that skill. How to Prepare
2. The interview framework
Work through the problem in this order. The times are the guide’s rough targets, not strict rules. Delivery Framework
1. Requirements (~5 min): Agree on the few features users need. These are functional requirements. Then identify the important qualities, such as response speed, scale, reliability, or security. These are non-functional requirements.
2. Core entities (~2 min): Name the main things you must store, such as User, Post, and Follow.
3. API or interface (~5 min): Show how a client asks the system to do things—for example, POST /posts to create a post. An API is simply the agreed way for programs to communicate.
4. Data flow, if useful: List the steps for a process such as “receive file → store file → process file → notify user.”
5. High-level design (~10–15 min): Draw the main components and follow each request through them. First make the core features work.
6. Deep dives (~10 min): Improve the design where it matters most: slow reads, heavy traffic, failures, or conflicting updates.
Do capacity maths when it changes a decision—for example, whether one database can handle the expected writes.
3. Core concepts
These are ideas you can apply regardless of which product you design. Core Concepts
- Networking: Services usually communicate through HTTP. For live updates, server-sent events let the server push messages to a client; WebSockets let both sides send messages over one lasting connection.
- API design: Define a small set of clear operations. REST is a common default: URLs name resources, and methods such as GET and POST say what to do.
- Data modeling: Decide what records to store and how they relate. A relational database such as PostgreSQL stores structured records in tables. Duplicating data can speed reads, but makes updates harder to keep correct.
- Database indexing: An index helps the database find records without checking every row. Add indexes for queries you actually need, such as finding orders by user_id; indexes also take space and add write work.
- Caching: Keep frequently read data in fast storage so fewer requests reach the database. Decide when a cached copy expires or is refreshed, or users may see old data.
- Sharding: Split data across multiple databases when one database is truly insufficient. The shard key decides where each record goes; it also decides which queries become easy or difficult.
- Consistent hashing: A way to distribute keys across servers so adding or removing a server moves only some keys, rather than reshuffling almost everything.
- CAP theorem: If database servers lose contact with one another, you may have to choose between refusing some requests to protect correctness and continuing to answer with potentially stale data. The right choice can differ within one product: a feed can tolerate delay; a seat booking may not.
- Numbers to know: Use rough estimates of request rate, storage, and delay to justify choices. Memory is much faster than a network trip, and a network trip across continents takes longer than one within a data centre.
4. Key technologies
Think of these as building blocks. Choose one when it solves a requirement you have identified. Key Technologies
Building block	What it does
Core database	Stores records such as users, orders, and posts. PostgreSQL is a common relational choice; DynamoDB is one NoSQL choice.
Blob storage	Stores large files such as images and videos. The database stores information about the file and a pointer to it.
Search database	Finds text or locations efficiently; Elasticsearch is an example.
API gateway	Receives client requests and routes them to services; it can also handle authentication and rate limits.
Load balancer	Spreads requests across several servers so one server does not carry all the traffic.
Queue	Holds jobs for workers to process, useful when work is slow or arrives in bursts.
Event stream	Keeps a sequence of events that multiple consumers can process, such as clicks for live analytics.
Distributed lock	Temporarily reserves a shared resource when several servers might change it at once.
Distributed cache	Holds frequently needed results in memory; Redis is a common example.
CDN	Keeps copies of content near users around the world, commonly for images and videos.


5. Common patterns
A pattern is a recurring solution to a recurring problem. Several may appear in one design. Common Patterns
- Live updates: Start with clients checking periodically if that is sufficient. Use server push when updates must arrive promptly.
- Long-running tasks: A server accepts the request quickly; a worker does the slow job later. Track its status and handle failures.
- Contention: Two people may try to buy the last item. Use a transaction or another coordination method so it is sold only once.
- Scaling reads: First improve queries and indexes; then consider database replicas, caches, and CDNs.
- Scaling writes: If measured write traffic exceeds capacity, consider batching, queues for bursts, or splitting data across servers.
- Large files: Let clients transfer files directly to file storage using temporary permission links, rather than sending every byte through the application server.
- Multi-step processes: Track a process such as payment → order creation → notification so it can recover safely if a step fails.
- Proximity search: Use a location index when you must efficiently find nearby drivers, shops, or users at large scale.
6. Question breakdowns
The final section is a practice catalogue, arranged from easier questions such as Bitly and Dropbox to harder ones such as Uber, Google Docs, payments, and a flash sale. Each question gives you a product in which to apply the same framework. For a first attempt, try Bitly: define how a long URL becomes a short one, how a visit finds the original URL, where the mapping is stored, and what might become slow as visits grow.
